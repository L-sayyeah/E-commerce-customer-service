# DST 与 Query Rewrite 多轮开发基线

新增 30 段对话、81 个已逐轮标注的用户轮次。覆盖售后切到另一地区的政策再返回、换单及顺序指代、歧义、工单、长历史、助手示例污染、地区和支付渠道继承，以及完整问句应直查。使用模拟订单及仓库政策标注。30 段对话属于开发集，正式验收按独立复核和每类至少 101 段对话的口径统计。

## 状态与改写

回放实际 DST、上下文节点和规则意图路由。助手消息保留在近期历史中，DST 只应用用户消息。预期不检索、直接检索、改写和澄清分开打分。订单地区的模拟工具事实仅用于核对金标。没有真实订单查询、模型分类、最终回答生成或写操作。

| 指标 | 结果 |
|---|---:|
| 已标注订单、歧义及适用工单槽位逐轮全对 | 78/81 |
| 意图正确 | 79/81 |
| 检索处理方式正确 | 76/81 |
| 应改写轮次中，实际触发改写 | 6/10 |
| 应改写轮次中，触发且改写符合关键条件 | 3/10 |
| 给定金标地区和订单引用后，同一改写模板符合关键条件 | 8/10 |

槽位全对率只包含本次标注的字段。政策地区单独通过检索查询校验，不能用 78/81 代表政策范围判断。金标 DST 对照注入期望的地区和订单引用，改写模板仍为当前实现。

## 真实检索对照

10 个应改写轮次有独立政策证据标注。每组使用同一个混合检索、加权融合及模型重排配置。这里直接比较各组查询的检索效果，并保留前一阶段是否实际进入检索的记录。即使规则意图走了工具分支，也可以离线检验改写文本的召回能力。参考查询根据项目政策编写，尚未独立人工复核。所有查询均不写业务库或索引。

## 复现的问题

- **跨政策话题串地区。** 日本订单 A 的引用仍然正确。插入欧盟政策咨询后，“回到刚才那单”生成了欧盟查询；给定日本地区后，正确证据重新进入 Top-5。韩国订单与美国政策插话的用例也复现了这一问题。
- **政策追问误用订单引用。** 查询日本订单后临时讨论欧盟政策，“那退款时效呢”生成了欧盟政策查询文本，但规则路由转到售后资格。独立检索测得能命中证据，实际聊天路径不会使用这个查询。
- **只有地区也可能改写不完整。** “那它呢”缺少前一轮的普通退货主题，“那发起以后多久能到账”缺少支付渠道。注入正确地区与订单引用后，这两题仍缺必要条件。
- **歧义和时间指代。** 连续查两笔订单后，“上一笔”仍引用最后一单。同时讨论欧盟、韩国后追问“签收后到底给多少天”，系统直接检索，金标要求先澄清。

## 客户澄清与地区隔离修复后的回归

7 段专项对话共 26 个用户轮次，已标注状态、意图和检索决策全部通过。四个聊天接口均验证了先澄清、再用原问题检索。客户仅答“对”时会再次确认。测试使用临时数据库和模拟检索，关闭 Checkpoint。越权订单的地区不会出现在提示里。

原 30 段对话复跑后，受评槽位全对从 78/81 到 80/81，应改写且满足关键条件从 3/10 到 8/10。未通过的改写仍涉及省略前文主题或支付渠道。此节记录离线状态与改写分数，真实检索表为改造前基线。
