# CustomServiceAgent 简历逐句拆解与面试追问

以简历截图中的 CustomServiceAgent 条目为范围。顺序为项目讲述、工作流与状态、检索、受控执行、评测口径。数字对应仓库里的开发实验和联调记录。

## 1. 一分钟讲述

> 我独立做了一个跨境电商售后客服后端。客户既会问“信用卡退款多久到账”这种政策问题，也会问“我这单还能退吗”这种需要查订单的问题。我用 FastAPI 接收请求，LangGraph 父图根据当前会话和用户诉求调度政策、订单和工单子图。订单状态从 MySQL 读，退款或补发资格由规则服务初判，模型负责解释政策。查政策走向量和关键词混合检索，再用模型重排。复杂题逐项核对证据，只对缺项补查。用户需要人工跟进时，可以确认后提交工单，数据库唯一约束保证同一次提交重试只产生一张工单。我用多轮对话回放、检索对照和数据库断言分别验证这些行为。

把这段背后的例子讲清楚，比一次报完所有技术名词更有说服力。

## 2. 项目简介和技术栈

### 用户问“这单能补发吗？顺便说一下政策”，系统做了什么？

1. 验证请求凭证和会话归属，从历史解析“这单”。
2. 父图调用订单子图。工具核对订单属于当前客户，再读取物流等事实，规则服务给出“可申请补发、需审核”等初判。
3. 如果用户同时问适用政策，父图把已核实的地区和物流条件交给政策子图检索，随后汇总事实、规则结果和政策参考。
4. 如果用户要人工跟进，系统提示确认并提交工单。显式建单接口写入工单与操作日志，客户可以查进度。资金退款和实际出库补发由后续人员或业务系统处理。

政策问答解决“规则是什么”，订单查询解决“事实是什么”，规则服务解决“按这些事实目前如何初判”，工单解决“谁来后续跟进、进度到哪”。 [父图](../app/agents/graph.py) · [节点](../app/agents/nodes.py) · [售后规则](../app/services/aftersales_rule_service.py)

### 每项技术为什么在这里？

| 技术 | 在本项目中的职责 |

### 普通接口与 SSE 有什么不同？怎么排查一次请求？

普通接口等待最终结果，再返回一次 JSON。SSE 在同一条 HTTP 连接上让服务端依次发送事件。普通知识流可以逐段发送答案，Agent 流会发送意图等事件，政策答案可在审查后一次发送。服务端用 trace ID 关联请求、检索记录和 Agent 节点。排查答错时依次看意图是否正确、槽位是否正确、召回和重排有没有保住证据、生成有没有遵守证据。建单成功与否还要看工单与操作日志。 [聊天接口](../app/api/v1/chat.py) · [日志查询](../app/api/v1/admin.py)

### 你的 Multi-Agent 如何协作？为什么用子图？

一个父图负责上下文和路由，三个专业子图分别处理政策、订单和工单。父图把任务种类、问题、会话及必要的订单或工单引用打包成 `TaskEnvelope`。子图返回白名单字段构成的 `TaskResult`，例如订单事实、规则结果、政策来源和动作轨迹。子图有各自的状态，身份由服务端运行时注入。已落地的订单加政策组合按预设依赖串行运行。政策子图内部可拆分证据问题；多子图自主协商及其端到端收益还没有正式评测。 [父子图协议](../app/agents/subgraphs.py) · [LangGraph 子图文档](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

### DST、改写、Checkpoint 和客户澄清怎么区分？

- **DST** 从已授权会话的用户消息跟踪当前订单、工单、改口及政策地区。模型生成的助手文本不会被当成客户新提交的槽位值。
- **Query Rewrite** 把已确定的上下文写进检索问句。比如客户继续问欧盟退款时效，可以给检索补上欧盟。主题或支付渠道的省略仍有未通过用例。
- **客户澄清** 处理两种指代都成立的情况。日本订单处理期间临时查欧盟政策，随后问“那退货规则呢”，系统先请客户选择。下一轮用选定地区继续原问题；会话消息保存澄清标记。
- **Checkpoint** 保存图的运行状态。客户确认是下一轮对话，恢复原问题依赖已保存的会话消息。关闭 Checkpoint 的专项测试也通过了澄清和续答。 [多轮实现](../app/agents/dialogue_state.py) · [多轮回归](multiturn-evaluation-2026-11-04.md)

## 3. 混合检索与 Agentic RAG

### 知识怎么入库，查询怎么跑？

知识按 Markdown 标题切分，长段再递归切分并保留重叠；MySQL 记录文档和切片，Milvus 建向量索引，Elasticsearch 建全文索引。查询时默认每路召回最多 20 条，按 `chunk_id` 合并，融合后取候选窗口，再用模型重排。基础固定对照最终取 5 条。Reranker 失败、超时或返回条数不完整时，服务按融合顺序降级，并记录状态。 [入库与融合](../app/services/knoewledge_service.py) · [检索与重排](../app/services/rag_service.py)

### 加权、RRF、Rerank 分别在哪一步？

- **加权融合** 默认用 `0.7 × 向量分数 + 0.3 × 归一化 BM25 分数`。向量分数截断到 0–1，BM25 分数除以同轮最高值。
- **RRF** 将某个片段在各路的 `1 / (60 + 名次)` 相加，名次从 1 起，未召回的路不贡献。它是同一融合层的备选。
- **模型 Rerank** 在融合后重新判断查询和候选片段的相关性。固定 Top-5 基线使用加权融合和同一个 Reranker。RRF 对照也经过该 Reranker。

BM25 更容易保住“首响”“质检”等术语，向量检索帮助匹配“多久第一次回复”“仓库检查通过”这类表达。两路分数尺度不同，所以加权前处理分值，RRF 则使用名次。 [融合代码](../app/services/knoewledge_service.py) · [RRF 定义](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

### 面试官追问 BM25、Embedding、HNSW 时怎么答？

BM25 给能区分文档的稀有词更高权重，同一个词反复出现的收益逐渐饱和，同时考虑文档长度。Embedding 把文本映射到向量空间，用余弦相似度衡量语义接近程度。HNSW 是 Milvus 用来加速向量近邻查找的图索引，通过近似搜索在速度和召回之间折中。模型重排的输入是查询和候选片段，适合在较小候选集上做更细的相关性比较。候选阶段完全没有找回的片段，重排也无法恢复，因此复杂路线还需要定向补检。 [Milvus 配置与查询](../app/services/milvus_service.py) · [重排服务](../app/services/rerank_service.py)

### 分差断层怎么截断？

相邻重排分数相减，找最大分差。默认至少 0.12，且至少是其他分差最大值的两倍。满足条件才把断层当作可能的高相关范围。普通路线只有在识别为单诉求且没有明显例外信号时才截断。复杂题的证据核对会看到完整的首轮候选窗口，首轮基础 Top-5 保留。这是减少误删的策略，分差不能证明断层之后没有关键条款。 [断层实现](../app/services/adaptive_retrieval.py) · [调用条件](../app/services/rag_service.py)

### 你的 Agentic RAG 哪里有决策？

原问先走基础检索和重排。复杂聊天保留基础 Top-5，拆成最多三个可核对的证据点，对照基础证据逐项检查。每个缺项可以定向查候选，整个请求最多再做一次改写或扩窗尝试。最多补两条证据，整个复杂检索的候选评分预算为 60 对，证据核对与补查共享 15 秒。15 秒以补充流程为口径，服务端总耗时还包括基础检索、重排和最终生成。

例子是“重复投诉，原工单未关闭，优先级、首响、建单怎么办”。三个证据点分别是 high 优先级、4 小时内首响和原工单复用。原版只按一条普通问题处理，漏了证据。修复后先逐项核对，齐全就停止。另有一道日本电子产品题通过定向补查找回了故障证明要求。 [补检代码](../app/services/adaptive_retrieval.py) · [逐题回归](agentic-rag-regression-2026-11-04.md)

### 逐字引用校验到底证明了什么？

模型给出候选片段编号和它认为支持子问题的逐字原文。代码校验编号在范围内，且引文是该片段正文的真实子串。失败就记为证据未确认。它能发现引文编造和引用编号错配。政策是否适用、证据是否足以推出结论，仍需结合地区、条件、规则及评测判断。校验主要服务于证据覆盖判定，最终答案的每句话没有因此自动得到验证。 [引用校验](../app/services/adaptive_retrieval.py)

## 4. 受控执行、安全和幂等

### 为什么资格判定交给规则，模型还参与哪些步骤？

订单数据和地区窗口可以由规则复核。比如日本普通退货窗口为 14 天，第 20 天超过普通窗口，质量例外需进一步核验。规则服务负责资格初判，模型可参与意图分类、检索拆解、证据判断、政策解释和回复审查。回复审查降低“保证退款”等越界承诺的风险，执行权限由服务端独立检查。 [售后规则](../app/services/aftersales_rule_service.py) · [回复审查](../app/agents/guardrails.py)

### SHA-256、RBAC、归属校验分别防什么？

| 防线 | 面试口径 |
|---|---|
| 凭证 | 客户端带 Bearer token，服务端计算 SHA-256 摘要并查配置里的身份。SHA-256 在这里是哈希，凭证是高熵随机 token。 |
| RBAC | 服务端身份包含客户或管理员角色。知识维护、管理日志及工单状态处理等走角色检查。 |
| 归属校验 | 普通客户查单、查工单、续聊时仍需核对资源归属。知道别人订单号不代表获得权限。 |

提示词可以影响分类与措辞。实际查询和写入通过限定的业务方法及鉴权进行。这个项目的工具目录没有通用 Shell，模型生成的命令文本没有对应工具能力。当前凭证方案是服务端配置登记，轮换和撤销需要更新配置并重启。 [认证](../app/core/auth.py) · [查单归属](../app/services/order_service.py) · [运行说明](../RUNTIME.md)

### 同一工单请求同时来了两次会怎样？

1. 客户端对同一次提交复用 `Idempotency-Key`，服务端把用户 ID 和该键一起哈希作为唯一请求键。
2. 服务端对规范化业务参数另算摘要。已有同键同参数的请求返回原工单号，同键异参返回 HTTP 409。
3. 并发时两个请求可能都没查到旧记录。MySQL 唯一约束阻止第二条写入。冲突方回滚后重查，取到先提交的工单。
4. 工单和创建日志在同一事务。若提交成功后、回复之前断线，重试仍能取回原工单。

实际用 MySQL 验证过 20 个并发同键请求全部返回同一工单号，数据库只产生一条工单和一条创建日志。也验证了提交后断开 TCP 再重试。客户端另换新键的相似请求属于业务去重范围，当前幂等保证适用于同一次提交的原键。 [工单实现](../app/services/ticket_service.py)

## 5. 评测数字怎么讲

### P@k、R@k、nDCG@k、MRR@k 和 Context Precision 有什么区别？

| 指标 | 面试解释 |
|---|---|
| Precision@k | 前 k 条里相关条数除以 k。 |
| Recall@k | 前 k 条命中的已标注相关证据数除以标注相关证据总数。 |
| nDCG@k | 给排得靠前的高相关结果更多分，再除以理想顺序的得分。 |
| MRR@k | 首个相关结果的名次取倒数，前 k 无命中得 0，再对题目取平均。 |
| Context Precision | 本报告口径是实际入模片段中匹配已标注证据的比例，对题目取平均。分母随实际入模数量变化。 |
| 全证据覆盖 | 一题要求多个证据组时，所有组都有命中才记通过。 |

例如，一题有 2 个必需证据，系统返回 5 条只命中 1 个，P@5 为 20%，Recall@5 为 50%，全证据覆盖失败。如果命中的证据排在第二，单题倒数名次为 0.5。 [实跑评分](../app/scripts/eval_live_rag.py)

### 简历上的三组提升有什么关系？

| 数字 | 正确比较对象 | 面试边界 |
|---|---|---|
| Context Precision 26.0% → 54.7%，片段 5.0 → 3.45 | 20 道政策开发题，固定 Top-5 对比早期 Agentic RAG。 | 上下文更精简，同一实验的完整证据从 100% 降到 95%，P95 从 5.91 秒升到 10.54 秒。 |
| 全证据覆盖 16/18 → 17/18 | 18 道回归题，固定 Top-5 对比保留基础证据、定向补查的版本。 | 只多补齐 1 题。固定版 P95 为 8.67 秒，限时 Agentic 版为 19.89 秒。 |
| P95 42.8 秒 → 19.9 秒 | 同一批 18 题，对比补充预算 35 秒与 15 秒的两版 Agentic。 | 两版都覆盖 17/18。这里是 Agentic 内部优化，样本小，P95 对最慢一题很敏感。 |
| 多轮改写瓶颈在槽位抽取 | 10 个需改写轮次，同一检索器下原问 7/10，预测 DST + 改写 8/10，金标 DST + 同一改写模板 10/10。 | 说明状态和地区选择是这批题的重要瓶颈。支付渠道、前文主题等改写缺项仍有剩余。 |

这些数字来自不同批次。应把策略、样本数和基线说全，特别是 42.8 秒的基线。 [20 题实验](evaluation-development-2026-11-04.md) · [18 题回归](agentic-rag-regression-2026-11-04.md) · [多轮评测](multiturn-evaluation-2026-11-04.md)

### 960 条、20 题、81 轮分别是什么？

960 条是 8 类候选素材，每类 120 条。20 题是有证据标注、真实跑过策略对照的政策开发集。81 轮来自 30 段多轮开发对话，轮次和独立对话数分开计算。后来补了 7 段客户澄清专项共 26 轮；原 81 轮状态回放中，所标槽位全对从 78/81 到 80/81，改写符合关键条件从 3/10 到 8/10。新实现的真实召回复测尚无结果。正式验收需要独立复核，已统计的正式样本仍为 0。 [评测数据说明](../app/data/eval/v1/README.md) · [多轮结果](multiturn-evaluation-2026-11-04.md)

### LLM-as-Judge 怎么校准？这个分数能信到什么程度？

Faithfulness 只对照实际入模证据，Answer Relevancy 对照问题和用户目标，Answer Correctness 对照必答事实及禁止断言。三项分开给评审材料，隐藏策略名称。8 条合成校准题上，三项与预设参考的精确一致分别为 7/8、7/8、8/8。回答和 Judge 使用相同模型，部分忠实度评分缺失，独立人工验收尚未完成。越权、写入次数和工单状态用程序及数据库断言核对。 [评测报告](evaluation-development-2026-11-04.md) · [RAGAS 论文](https://aclanthology.org/2024.eacl-demo.16/)

## 6. 面试中如何回答“现在最大的缺点？”

> 复杂检索的额外调用仍贵。修复后在 18 题里比固定 Top-5 多覆盖 1 题，P95 仍从 8.67 秒升到 19.89 秒。下一步的核心是把确实缺关键证据的请求筛出来，扩大独立验收，确认增益能覆盖代价。多轮侧已经用金标 DST 对照定位了串地区，还要继续验证支付渠道和主题继承。

截图中的“出口审查拦截保证退款”宜口述为**检查并尝试改写越界承诺**；“分差断层截断避免切掉例外”宜口述为**遇多证据或明显例外信号时保留基础证据，降低误删概率**；“定位瓶颈在槽位抽取”可具体说成**订单与政策地区混用是这批题的重要问题，模板仍会漏主题和支付方式**。简历链接也需确认指向实际用于展示的仓库，当前本地 `origin` 与截图地址不同。
